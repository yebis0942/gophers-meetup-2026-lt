ccgo is 何？
3
まず問いだけ置きます。ccgo は何をしているのか。次のスライドから modernc.org/sqlite を入口にして説明します。

modernc.org/sqlite の裏側

import _ "modernc.org/sqlite"
  • cgo を使わずに SQLite を利用できる Go パッケージ
  • 中身は、SQLite の C 言語ソースを ccgo で Go に変換した生成コード
  • 変換は配布前に済んでいる。利用者は普通の Go パッケージとして import するだけ
  • CGO_ENABLED=0 のままビルド・クロスコンパイルできる
4
まず modernc.org/sqlite です。database/sql のドライバとして import するだけで使えて、cgo は要りません。中身は C の SQLite を ccgo で事前に Go へ変換したコードです。今日はその生成コード側を見ます。

今日はデータ構造に絞ります。struct、union、bit-field の 3 つです。ccgo が守ろうとしているのは C のメモリ配置で、そのために C のポインタは uintptr として扱われます。出てくる数値は v1.60.1 の darwin/arm64 版のものです。

C 言語の struct: sqlite3_value

  • sqlite3_value は SQL の値 1 つを表す struct
  • フィールドは宣言順に並び、アラインメントに合わせて配置される
  • コメントの数字が各フィールドの offset（64 bit 環境）
struct sqlite3_value { union MemValue u; /* 0 */ char *z; /* 8 */ int n; /* 16 */ u16 flags; /* 20 */ u8 enc; /* 22 */ u8 eSubtype; /* 23 */ sqlite3 *db; /* 24 */ /* … */ };
7
struct の例は sqlite3_value です。SQL の値 1 つを表す構造体で、このあと出てくる union の MemValue もこの中にあります。C ではフィールドが宣言順に並び、各フィールドの offset が決まります。

ccgo の struct: Go の struct になる

  • C 言語の struct は Go の struct になる。フィールド名に F、型名に T が付く
  • ポインタは型を問わず uintptr（char * も sqlite3 * も）
  • uintptr を struct のポインタに変換して、フィールドを読む
  • offset とサイズは C 言語と一致する（Fflags は 20、全体は 56 byte）
type Tsqlite3_value = struct { Fu TMemValue Fz uintptr Fn int32 Fflags Tu16 Fenc Tu8 FeSubtype Tu8 Fdb uintptr // … }
sqlite3_bind_value より
libc.Int32FromUint16( (*Tsqlite3_value)(unsafe.Pointer(pValue)).Fflags)
8
生成コードでは C の struct がそのまま Go の struct になります。ポインタはすべて uintptr で、使うときに struct のポインタへ変換してフィールドを読みます。unsafe.Offsetof で測ると flags は 20、全体は 56 byte で、C と同じ配置です。配置がずれる場合、ccgo はパディング用やアラインメント用のフィールドを足して合わせます。

C 言語の union: MemValue

  • sqlite3_value は SQL の値を 1 つ保持する
  • union の各メンバは同じ場所を共有する。大きさは最大のメンバに合わせる
  • flags の MEM_Int / MEM_Real などを見て、どのメンバとして読むかを決める
union MemValue { double r; i64 i; int nZero; const char *zPType; FuncDef *pDef; } u;

union の例は MemValue です。整数と実数を別々に持つのではなく、同じ 8 byte を用途に応じて使い分けます。どれとして読むかは、別に持っている flags で判断します。

ccgo の union: ゼロ長配列で表す

  • [0]T のフィールドはサイズ 0。全員が offset 0 に並ぶ
  • 実体を持つのは Fr float64 の 8 byte だけ
  • 読むときは先頭アドレスを目的の型のポインタに変換する
  • u は sqlite3_value の先頭にあるので offset の加算がない
type TMemValue = struct { Fi [0]int64 FnZero [0]int32 FzPType [0]uintptr FpDef [0]uintptr Fr float64 }
sqlite3_bind_value より（整数のとき）
*(*Ti64)(unsafe.Pointer(pValue))
同じ関数内（実数のとき）
*(*float64)(unsafe.Pointer(pValue))
10
Go には union がないので、ccgo はゼロ長配列を使います。Fi や FnZero はサイズ 0 で、すべて同じ offset 0 に乗ります。実際に読むときは Fi[0] ではなく、先頭アドレスを int64 のポインタとして読みます。数値変換ではなく、同じ bytes の読み替えです。

C 言語の bit-field: SrcItem.fg

  • unsigned x:1 は 1 bit のフィールド。FROM 句の要素の属性を 1 つの整数に詰める
  • C 言語ではふつうのフィールドとして読み書きでき、mask / shift はコンパイラが生成する
  • Go で書くなら flags uint32 と const isSubquery = 1 << 2 の組み合わせに当たる
struct { u8 jointype; unsigned notIndexed :1; unsigned isIndexedBy :1; unsigned isSubquery :1; /* … */ } fg; pItem->fg.isSubquery = 1;

11
bit-field の例は SrcItem.fg です。FROM 句の要素に付く属性を 1 bit ずつ詰めていて、たとえば bit 2 の isSubquery は、テーブルではなくサブクエリであることを表します。C では pItem->fg.isSubquery = 1 のように普通のフィールドとして書けて、mask や shift はコンパイラが裏で生成します。Go でいえば、flags uint32 に const で bit を定義して手でビット演算するのと同じことです。なお jointype の後ろに 3 byte のパディングがあり、bit を詰める整数は +4 から始まります。

ccgo の bit-field: 整数と mask になる

  • コンパイラが隠していた mask / shift を、ccgo は Go のコードとして書き出す
  • bit-field の名前は消え、F__ccgo4 uint32 1 つにまとめられる
  • +24 で fg、+4 で整数。読むときは mask して右シフト、書くときは libc のヘルパーが対象 bit だけを更新する
Ffg struct { Fjointype Tu8 F__ccgo4 uint32 }
読み出し（isSubquery）
*(*uint32)(unsafe.Pointer(pItem + 24 + 4))&0x4>>2
書き込み（isSubquery = 1）
libc.SetBitFieldPtr32Uint32(pItem+24+4, libc.Uint32FromInt32(1), 2, 0x4)
12
C ではコンパイラが隠していたビット演算を、ccgo は Go のコードとして書き出します。生成型では bit-field の名前は消えて、F__ccgo4 という uint32 になります。読むときは 0x4 で mask して 2 bit 右シフト、書くときは libc のヘルパーが read-modify-write で隣の bit を壊さずに書き換えます。

uintptr とメモリの寿命

  • SQLite の標準 allocator は、匿名 mmap で確保した Go ヒープ外の領域を使う
  • Go の GC はこの領域を移動も回収もしない。寿命は SQLite / libc が管理する
  • free 後はアクセスできず、realloc では領域が移ることがある。ここは C 言語と同じ
  • Go が管理するオブジェクトのポインタを uintptr にして保持する真似はしない
SQLite_sqlite3MemMalloc
modernc.org/libcXmalloc
modernc.org/memoryAllocator
匿名 mmapGo ヒープ外
13
ここまで uintptr でポインタ演算をしてきましたが、これが成り立つのは、メモリが Go ヒープの外にあるからです。libc の allocator が mmap した領域なので、GC は動かしも回収もしません。逆に、Go のオブジェクトのポインタを uintptr で持ち回るのは GC から見えなくなるので危険です。realloc が成功したら返されたアドレスを使い、失敗したときは古い領域が残る、というのも C と同じです。libc v1.77.1 の通常ビルドで、darwin/arm64 と linux/amd64 を確認しました。

まとめ

  • struct: Go の struct になり、ポインタは uintptr で持つ
  • union: ゼロ長配列で同じ offset を表し、同じ bytes を別の型として読む
  • bit-field: 名前は消え、整数を mask / shift で読み書きする
  • 生成コードの奇妙な型や数字は、C 言語の配置と対応させると読める

まとめです。生成コードの型や数字は、元の C のメモリ配置と対応させると読めます。cgo なしで動く SQLite の中にも、C 由来のメモリ表現と寿命管理がそのまま残っています。今日は触れませんでしたが、関数ポインタや可変長引数、ローカル変数のアドレスの扱いなど、ccgo にはほかにも面白い変換がたくさんあります。

おまけ: 末尾の可変長配列（FLEXARRAY）

  • SrcList の a は柔軟配列メンバ。ヘッダの直後に要素が続く
  • 生成された TSrcList には a がない（要素数が実行時に決まる）
  • a[i] は「先頭 + 8 + i × 80」のアドレス計算になる
  • [0]uint64 は、サイズ 0 のまま 8 byte のアラインメントだけを補う
struct SrcList { int nSrc; u32 nAlloc; SrcItem a[FLEXARRAY]; };
type TSrcList = struct { F__ccgo_align [0]uint64 FnSrc int32 FnAlloc Tu32 }
pItem = pTabList + 8 + uintptr(v1)*80
15
おまけです。SrcList は FROM 句の入力元一覧で、8 byte のヘッダの直後に 80 byte の SrcItem が並ぶ柔軟配列メンバを持ちます。ccgo は柔軟配列メンバを Go の struct から外し、a[i] へのアクセスを先頭 + 8 + 添字 × 80 のアドレス計算として生成します。外す理由はソースに書かれていませんが、末尾にサイズ 0 のフィールドを置くと Go が struct の末尾にパディングを足してサイズが C とずれるため、と考えられます。
